# ADR 0012 - Transactions and production confirmation (screens M03, M04, M15)

- Status: accepted
- Date: 2026-11-12

## Context
Phase 15 (cards P15-01 to P15-20, [task index](../tasks/README.md)) adds manual transaction control (`Valider` / `Annuler`, pending count, a guard on every way out) and the production confirmation of mockup M15 to SQLite, PostgreSQL, MySQL and SQL Server in both heads. Before it every statement ran auto-committed on the one connection of a session, and nothing but `Analyser` asked a question on a Production connection. The shared decisions are in [transactions-recipe.md](../tasks/phase-15/transactions-recipe.md); the end-to-end evidence and the owner's checklist are in [verification/transactions.md](../verification/transactions.md).

## Decision
- **The transaction belongs to the session, not to the tab.** A profile has one connection shared by every query tab, the explorer, the table designer, the grid commit and the plan reader; a transaction per tab would need one extra connection per tab (connect cost, SSH tunnel reuse, server slots, the explorer and the tab seeing different data). `SessionTransaction` is exposed as `ConnectionSession.Transaction` (a derived session for another database of the server has its own). The toggle, pill and buttons are in every query tab and mirror the session; a statement run in tab B while tab A has a transaction open runs inside it, and the journal records the tab title.
- **Two modes, `AutoCommit` (default everywhere, no new setting) and `Manual`.** In `Manual` the app issues the begin statement lazily, right before the first statement that is not read-only (`StatementTraits.ReadOnly` false; unknown statements, `CALL`, `EXEC`, `DO` count as not read-only). Read-only statements run outside any transaction until one is open: an idle transaction left open by a `SELECT` holds a snapshot and locks on a production server.
- **State machine** `None` / `Open` / `Failed`. `Failed` exists on PostgreSQL only (every statement after an error answers `25P02` until `ROLLBACK`); the app refuses later statements upfront with `tx.failed` and only `Annuler` is offered. A `BEGIN` / `START TRANSACTION` typed by the user opens a transaction in any mode (count 0), typed `COMMIT` / `ROLLBACK` close it: typed statements are honoured, not fought.
- **The server is the truth: `ITransactionProbe`**, an optional interface of `IDatabaseConnection` (`Squill.Data`), implemented by the four connections (Oracle does not: its toggle is disabled with `tx.unsupported`). The state is tracked by the app and resynchronised through the probe after an error inside an open transaction, after statements that may change the transaction (`CALL`, `EXEC`, `DO`, `SET autocommit`, `SET IMPLICIT_TRANSACTIONS`, `PRAGMA`, `LOCK TABLES`) and before `Valider` / `Annuler`. A probe that answers "unknown" changes nothing; it never throws to the caller.
- **Statement vocabulary is pure and shared** (`Squill.Sql/Transactions`: `StatementTraits`, `StatementClassifier`, `TransactionSql`) so the heads, the guard and the estimator classify a statement the same way; per-dialect begin, commit, rollback and savepoint text lives in `TransactionSql`.
- **Pending count and journal.** The pill and the status bar count the statements executed successfully since the transaction opened that are not read-only (failed statements are not counted). `SessionTransaction.Journal` keeps text (cut at 500 characters), tab title, time and rows affected, at most 200 entries; the count keeps counting beyond that. `Valider` and `Annuler` write `COMMIT` / `ROLLBACK` history entries with the profile.
- **Savepoint scopes for the grid commit and the designer apply.** `SqlRunner.BeginAsync` inside a user transaction would break it (MySQL `BEGIN` commits, SQLite refuses a nested `BEGIN`, SQL Server nests and the inner `COMMIT` only decrements `@@TRANCOUNT`). Inside an open transaction both use `SAVEPOINT` / `RELEASE` (PostgreSQL, MySQL, SQLite) or `SAVE TRANSACTION` / `ROLLBACK TRANSACTION name` without release (SQL Server); a failure rolls back to the savepoint only (which also recovers a PostgreSQL `Failed` state); their statements count as pending. The unnamed SQL Server `ROLLBACK` (which rolls back every nested level) is used by `Annuler` only.
- **Implicit commit and statements that cannot run in a transaction** are decided from `StatementTraits`. A statement with `ImplicitCommit` (MySQL DDL and friends) run while a transaction is open asks `Valider et exécuter` / `Annuler` and leaves the state `None`; a statement with `CannotRunInTransaction` (PostgreSQL `VACUUM`, `CREATE DATABASE`, `CREATE INDEX CONCURRENTLY`; SQL Server `CREATE/ALTER/DROP DATABASE`, `BACKUP`, `RESTORE`; SQLite `VACUUM`, `ATTACH`, `DETACH`) is refused with `tx.cannotRun` and never sent, because the server would abort the transaction.
- **Every way out asks.** Closing the last query tab of a session, `Déconnecter`, switching `Manual` to `AutoCommit` and quitting ask `Valider` / `Annuler les modifications` / `Retour` (only `Annuler` / `Retour` on `Failed`); closing a tab while another tab of the session stays open asks nothing. The question lists the connection, environment, count and the first five journal entries; its `Valider` is the confirmation, a Production session does not ask a second time. A failing commit keeps everything open and shows the error. Both heads intercept the window close with a cancel-then-close-again pattern (`WorkspaceViewModel.PrepareExitAsync`). `ConnectionSession.DisposeAsync` sends a best-effort `ROLLBACK`; a crash or kill is rolled back by the server when the connection drops.
- **Production confirmation (M15)** applies when the profile environment is `Production`, to `Run` / `Run all` (one dialog per run, after the parameter prompt), `Valider`, the grid commit and the designer apply. It never applies to `Analyser` (which keeps its plain confirmation of ADR 0010), `Expliquer`, read-only statements or other environments. `ProductionGuard` triggers on `ModifiesData`, `ChangesSchema` and unknown / `CALL` / `EXEC` / `DO` statements and on a typed `COMMIT`. **Typed confirmation** (the user types the database name, the SQLite file name, or the profile name when there is no database; compared ignoring case after trimming; the red confirm button stays disabled until it matches) only for destructive statements: `DELETE` or `UPDATE` without `WHERE`, `TRUNCATE`, any `DROP`, `ALTER ... DROP`. Other triggering statements get the same dialog without the field. **`Entrée` is `Annuler`**: the confirm button is never the default and never reacts to `Entrée`. The checkbox "run in a transaction and do not commit automatically" is shown when every statement can run in a transaction on the engine, checked by default; in `Manual` it is checked and disabled; in `AutoCommit` leaving it checked switches the session to `Manual`.
- **Estimated impact.** `ImpactEstimator` asks the plan reader (`PlanMode.Estimated`, never executes) for a single `INSERT` / `UPDATE` / `DELETE`, under a hard cap of 3 s, never when the transaction is `Failed`. The figure is the estimated rows of the first descendant of the plan root that reports them (the root of a data-modifying plan reports 0 on PostgreSQL). `INSERT ... VALUES` is not estimated. SQLite, an engine refusal, a timeout or unplannable parameters give no figure and no error; the confirm button then says `Exécuter`. A figure is always worded as an estimate and formatted in the user's number format.
- **Per-engine matrix**

| | SQLite | PostgreSQL | MySQL 8.4 | SQL Server |
|---|---|---|---|---|
| begin / commit / rollback | `BEGIN` / `COMMIT` / `ROLLBACK` | same | `START TRANSACTION` / `COMMIT` / `ROLLBACK` | `BEGIN TRANSACTION` / `COMMIT TRANSACTION` / `ROLLBACK TRANSACTION` |
| savepoint | `SAVEPOINT` / `ROLLBACK TO` / `RELEASE` | same | same | `SAVE TRANSACTION` / `ROLLBACK TRANSACTION name`, no release |
| DDL transactional | yes | yes | no, implicit commit (asks) | yes |
| error inside a transaction | stays open | `Failed` | stays open | stays open (a doomed `XACT_STATE() = -1` cannot outlive its batch on 2022) |
| refused inside a transaction | `VACUUM`, `ATTACH`, `DETACH` | `VACUUM`, `CREATE/DROP DATABASE`, `CREATE INDEX CONCURRENTLY` | none | `CREATE/ALTER/DROP DATABASE`, `BACKUP`, `RESTORE` |
| probe | `sqlite3_get_autocommit` | `SELECT 1`: `25P02` is failed, else unknown | **always unknown** | `@@TRANCOUNT`, `XACT_STATE()` |
| planner figure for `DELETE` / `UPDATE` | none | child scan | table access of the JSON plan | child of the `Delete` / `Update` operator |

## Alternatives considered
- **One connection per tab** so that each tab owns a transaction. Rejected for this phase (cost above, and the explorer, designer and plan reader would need to learn which connection to use); listed under "Not done".
- **Begin eagerly when `Manual` is switched on.** Rejected: a `SELECT`-only session would hold a snapshot and locks open for hours on a production server. The begin is lazy, before the first modifying statement.
- **Typed confirmation for every modifying statement on Production.** Rejected: it trains the user to type the word without reading. Only destructive statements ask for it, the others get the dialog with the confirm button enabled.
- **Executing the statement to count the rows it would touch.** Rejected: only the planner estimate is available without side effects.
- **A `Staging` confirmation or a default mode per profile.** Left out: no setting and no per-environment behavior was asked for in this phase.

## Consequences
- The same flows (commit, rollback, failed script, typed `BEGIN`, DDL, grid and designer in a transaction, two tabs, close, disconnect, exit, Production and Staging) are checked on all four engines by one scenario (`tests/Shared/TransactionFlowScenario.cs`, plus `TransactionScenario` for the drivers); SQLite runs everywhere, the others in Podman or Docker.
- **Behavior change:** on a Production connection the grid commit and the designer apply now ask for a confirmation; before this phase only `Analyser` did.
- Every implementer of `IDialogService` has two more members (`ConfirmProductionAsync`, `AskTransactionAsync`).

## Known limits
- **Tabs of one session share the transaction.** A statement run in tab B while tab A has a transaction open runs inside it. Two tabs running statements at the same moment on one connection stays a limit of the app (the drivers fail one of them); `ConnectionSession.BeginOperation()` only disables `Valider`, `Annuler` and `Run` while another kind of operation runs.
- **MySQL**: DDL and a few other statements commit implicitly (the app asks first); MyISAM and other non-transactional tables are not detected; `ROLLBACK` does not undo them. **The MySQL probe is always "unknown"** (P15-06): `performance_schema.events_transactions_current` is reliable but denied to a user who only has privileges on their own schema, and `information_schema.innodb_trx` needs `PROCESS` and does not show a transaction that only read. The app therefore tracks the MySQL state itself, and a transaction ended by the server (deadlock rollback) is not noticed until the next error or `Valider`.
- **`SET autocommit`, `SET IMPLICIT_TRANSACTIONS`** and similar are allowed and only picked up by the probe; the app does not model them.
- **A connection lost mid-transaction** (SSH tunnel drop, server restart) is not reconnected: the server has rolled back, `Valider` fails, the app shows the error and says the session was lost.
- **No idle timeout and no automatic rollback**; a long transaction on a production server holds locks (PostgreSQL: it blocks vacuum). The status bar shows the duration.
- **The impact figure is a planner estimate**, capped at 3 s, absent on SQLite, for `INSERT ... VALUES` and when the engine refuses the plan; it can be far from the real count and never blocks the run.
- **Shortcuts** `Ctrl+Alt+C` / `Ctrl+Alt+Z` are `AltGr+C` / `AltGr+Z` on many keyboard layouts and may type a character in the editor; this was not checked on AZERTY by an agent session (checklist).
- **Quit paths that cannot be intercepted**: a killed process, a power loss and an OS shutdown that does not give the application time are not guarded (the server rolls back); the macOS application-menu `Quit` reaching `ShutdownRequested` is from the Avalonia contract, not observed. The WinUI head has no `Quitter` menu item, only the window close button.
- **Windows were not driven end to end.** The WinUI and Avalonia screens were not compared with the M03 / M04 / M15 PNGs side by side by an agent session; see [verification/transactions.md](../verification/transactions.md) and sections 12 and 14 of [visual-spec.md](../design/visual-spec.md).

## Not done
Per-tab connections, a default mode per profile or environment, a `Staging` confirmation, isolation-level choice, read-only transactions, a savepoint UI, a long-transaction warning or idle timeout, a transaction in the native-client terminal tab (it is the client's own session), Oracle (keeps auto-commit), MariaDB.
