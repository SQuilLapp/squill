## 1. What exists today (audit of 2026-11-12, read before changing anything)

- **One connection per session.** `SessionManager.OpenAsync` opens one `IDatabaseConnection` per profile (plus its SSH tunnel); `ConnectionSession` is that connection, its schema and its tunnel. Every query tab, the explorer, the table designer, the grid commit and the plan reader of a profile use `session.Connection`. Another database of the same server opens a **derived session** (own connection, `Parent` set, closed with its root). There is no per-tab connection and **no operation gate**: `IsRunning` is per tab, two tabs of one session can already issue statements concurrently (the drivers then fail; known, not caused by this phase). `IDatabaseConnection.ExecuteAsync(sql, parameters, ct)` runs exactly one statement.
- **No transaction state anywhere.** All four drivers run in their default auto-commit mode. The only transactions are the short ones opened by `SqlRunner.BeginAsync/CommitAsync/RollbackAsync` (text `BEGIN` / `COMMIT` / `ROLLBACK`, `BEGIN TRANSACTION` ... on SQL Server) for the grid commit (`EditCommitter`) and the designer apply (`TableDesignerViewModel`), and the plan readers: PostgreSQL `BEGIN READ ONLY` (sees warning `25001` when a user transaction is open and then does not roll back), SQL Server `SAVE TRANSACTION` when `@@TRANCOUNT > 0` else `BEGIN TRANSACTION`, MySQL no wrapper. **`SqlRunner.BeginAsync` inside a user transaction would break it**: MySQL `BEGIN` commits the open transaction, SQLite refuses a nested `BEGIN`, SQL Server nests and the inner `COMMIT` only decrements `@@TRANCOUNT`, PostgreSQL warns and carries on.
- **Production today**: `ConnectionEnvironment.Production` colors the chrome (chip `PRODUCTION`, red tab marker) and `QueryTabViewModel.RunPlanAsync` asks `IDialogService.ConfirmAsync(plan.analyze.confirm.*)` before `Analyser` (P13-14). **Nothing else is guarded**: `Run`, `Run all`, the grid commit and the designer apply execute without a question. `IDialogService` has `ConfirmAsync(title, message)` (plain two-button box) and no richer dialog.
- **Statement classification today**: `Squill.Sql/Plans/PlanEligibility` (token-based: head keyword, private `WritesData` scan for `INTO` / `DELETE` / `MERGE` / `UPDATE` / `INSERT(`), `QueryTabViewModel.IsSchemaChange` (text prefix `CREATE` / `ALTER` / `DROP`), the parser records `UpdateStatement.Where` / `DeleteStatement.Where` (`Squill.Sql/Syntax/Statements.cs`). There is no shared "what does this statement do" type.
- **Plan reader** gives estimated rows: `PlanNode.EstimatedRows` (`Squill.Core/Plans`), `ConnectionSession.ExplainAsync(statement, parameters, PlanMode.Estimated, ct)` never executes and works for `INSERT` / `UPDATE` / `DELETE` on the four engines (`PlanEligibility.CanExplain`). **The root of a data-modifying plan does not carry the affected rows**: PostgreSQL `Delete on t (rows=0)` with the scan as its child (`rows=1000`), SQL Server the `Clustered Index Delete` operator and its child scan, MySQL the table access block. SQLite gives no estimate.
- **Closing**: `WorkspaceViewModel.CloseTabAsync` asks only for unsaved text and pending grid edits; `DisconnectAsync` removes tabs and disposes the session without asking; **neither head handles the window closing at all** (no `Closing` handler in `src/Squill.App.WinUI` or `src/Squill.App.Avalonia`).
- Heads: query toolbar in `Views/QueryTabView.cs` (WinUI, code-built) and `Views/QueryTabView.axaml` (Avalonia), status bar `Views/StatusBar.cs` / `StatusBar.axaml`, dialogs `Services/WinUiDialogService.cs` / `AvaloniaDialogService.cs`, `ModalWindow.cs` (WinUI).
- Tests: engine-neutral scenarios in `tests/Shared/*Scenario.cs`, run per driver by the test classes of `tests/Squill.Data.<Driver>.Tests` (Docker-gated for the servers, see [../phase-11/verification-recipe.md](../phase-11/verification-recipe.md)); Presentation tests with fake connections in `tests/Squill.Presentation.Tests` (`SqlRunnerTests`, `PlanTabTests`, `QueryTabViewModelTests`).

## 2. Decisions (final, the owner may change the flagged ones, see the report of the writing session)

1. **The transaction belongs to the session (the connection), not to the tab.** The connection is shared by every tab, the explorer, the designer and the plan reader, so a tab-level transaction would need one extra connection per tab (connect cost, SSH tunnel reuse, server connection slots, explorer and tab seeing different data); rejected for this phase. Consequences, written in the ADR: the toggle and the buttons are in every query tab and **mirror the session**; a statement run in tab B while tab A has an open transaction runs **inside** it; the journal records the tab title next to each statement. `SessionTransaction` is exposed as `ConnectionSession.Transaction`. Derived sessions (other database of the server) have their own.
2. **Modes.** `TransactionMode` `AutoCommit` (default for every environment, no new setting) and `Manual`. In `Manual` the app issues the begin statement **lazily, right before the first statement that is not read-only** (`StatementTraits.ReadOnly` false; unknown statements, `CALL`, `EXEC`, `DO` count as not read-only); read-only statements run outside any transaction until one is open (an idle transaction left open by a `SELECT` holds a snapshot and locks on a production server); once a transaction is open every statement runs inside it. The status bar says `Transaction manuelle` while the mode is `Manual` with nothing open.
3. **State.** `TransactionState` `None`, `Open`, `Failed` (PostgreSQL only: after any error inside an open transaction, until `ROLLBACK` / `ROLLBACK TO SAVEPOINT`; the other engines never enter it). Transitions:

| From | Event | To |
|---|---|---|
| `None` | non-read-only statement in `Manual` mode (begin issued first) | `Open` |
| `None` | the user's script runs `BEGIN` / `START TRANSACTION` / `BEGIN TRANSACTION` (any mode) | `Open` (opened by script, count 0) |
| `Open` | `Valider`, or the script runs `COMMIT` / `END` | `None` |
| `Open` or `Failed` | `Annuler`, or the script runs `ROLLBACK` | `None` |
| `Open` | statement error, PostgreSQL | `Failed` |
| `Open` | statement error, other engines | `Open`, then probe (section 4) |
| `Open` | statement with implicit commit (MySQL) after the user confirmed | `None` |
| `Failed` | any statement except `ROLLBACK` / `ROLLBACK TO` | refused by the app with the reason `tx.failed` (the server would refuse it too) |

4. **Truth from the server.** State is tracked by the app and **resynchronised** through the optional `ITransactionProbe` of the connection (P15-03) after: an error inside an open transaction, a statement whose traits say `MayChangeTransaction` (`CALL`, `EXEC`, `DO`, `SET autocommit`, `SET IMPLICIT_TRANSACTIONS`, `PRAGMA`, `LOCK TABLES`), and before `Valider` / `Annuler`. A probe that answers "unknown" changes nothing. The probe never throws to the caller.
5. **Pending statement count and journal.** The pill and the status bar count the statements **executed successfully since the transaction opened that are not read-only** (`1 instruction` / `N instructions`, plural through `UiText.FormatPlural`); a failed statement is not counted. `SessionTransaction.Journal` keeps for each such statement the text (cut at 500 characters), the tab title, the time and the rows affected, at most 200 entries (older ones dropped, the count keeps counting). The journal feeds the commit confirmation and the close dialog.
6. **Valider / Annuler.** Enabled when `State != None` and nothing else runs on the session (`BeginOperation` counter, section 6). `Valider` on a `Production` session asks for confirmation first (`ConfirmProductionAsync`, kind commit, lists the journal, no typed text). `Annuler` never asks. Both write a history entry (`COMMIT` / `ROLLBACK`, with the session's profile) so the audit trail shows them. After an error of `COMMIT` the state is kept and the error shown; if the probe then also fails the session is reported as lost (known limit, risk 8).
7. **Typed transaction statements are honoured, not fought.** `BEGIN` typed in `AutoCommit` mode opens a transaction (state `Open`, mode stays `AutoCommit`, `Valider` / `Annuler` appear), `COMMIT` / `ROLLBACK` typed close it. `SET autocommit` / `SET IMPLICIT_TRANSACTIONS` are allowed and only picked up by the probe; the app does not model them (known limit).
8. **Inside an open transaction the short transactions of the grid commit and the designer apply use savepoints** (new `SqlRunner` scope, P15-09): `SAVEPOINT` / `RELEASE` (PostgreSQL, MySQL, SQLite), `SAVE TRANSACTION name` and `ROLLBACK TRANSACTION name` without release (SQL Server). A failed grid commit rolls back to its savepoint only (and on PostgreSQL that also leaves the `Failed` state). The statements count in the pending count. They are refused with `tx.failed` when the state is `Failed`. A MySQL statement with implicit commit (designer `ALTER TABLE`) asks first (point 9).
9. **Implicit commit and statements that cannot run in a transaction** (decided from `StatementTraits`, P15-01): a statement with `ImplicitCommit` (MySQL DDL and friends) run while a transaction is open asks `tx.implicitCommit.*` (`Valider et exécuter` / `Annuler`) because it commits the pending work; after it ran the state is `None`. A statement with `CannotRunInTransaction` (PostgreSQL `VACUUM`, `CREATE DATABASE`, `CREATE INDEX CONCURRENTLY`...; SQL Server `CREATE/ALTER/DROP DATABASE`, `BACKUP`, `RESTORE`; SQLite `VACUUM`, `ATTACH`, `DETACH`) run while a transaction is open is **refused with a message** (`tx.cannotRun`), never sent (the server would abort the transaction).
10. **Closing with a transaction open** (`State != None`): closing the **last** query tab of a session, `Déconnecter`, switching `Manual` -> `AutoCommit`, and the application exit ask `Valider` / `Annuler` (rollback) / `Retour`; on `Failed` only `Annuler` / `Retour`. Closing a tab while another tab of the session stays open asks nothing (the transaction belongs to the session). The question lists the connection, environment, the count and the first five journal entries. The `Valider` answer of this dialog is the confirmation, a `Production` session does not ask a second time. A failing commit keeps everything open and shows the error. `ConnectionSession.DisposeAsync` sends a best-effort `ROLLBACK` before closing the connection (a crash or a killed process is rolled back by the server when the connection drops; SQLite by its journal).
11. **Production confirmation (M15).** Applies when `Profile.Environment == Production` to: `Run` / `Run all` (one dialog per run, after the parameter prompt), `Valider`, the grid commit, the designer apply. Never for `Analyser` (keeps the plain `ConfirmAsync` of P13-14), `Expliquer`, read-only statements, other environments. **What triggers it** (`ProductionGuard`, P15-12): a statement with `ModifiesData`, `ChangesSchema`, or an unknown / `CALL` / `EXEC` / `DO` statement; `COMMIT` typed in the script. **Typed confirmation** (the mockup shows it) only for `Destructive` statements: `DELETE` or `UPDATE` without `WHERE`, `TRUNCATE`, any `DROP`, `ALTER ... DROP`; the user types the **database name** (`Profile.Database`; SQLite: file name; no database: the profile name), compared ignoring case after trimming; the confirm button stays disabled until it matches. Other triggering statements get the same dialog without the field and with the confirm button enabled. **`Entrée` = `Annuler`** (Cancel is the default button, the confirm button is never the default and never reacts to `Entrée`).
12. **Dialog content** (all text through `UiText`, keys `prod.*` and `tx.*`): red header `PRODUCTION · <connection name> / <database>` with a warning icon; title (`Supprimer toutes les lignes de <table> ?` for a `DELETE` without `WHERE`, `Modifier toutes les lignes de <table> ?` for an `UPDATE` without `WHERE`, a generic `Exécuter cette instruction en production ?` / `Exécuter ces N instructions en production ?` otherwise); message with the figure when there is one (`elle supprimera environ 1 248 310 lignes (estimation du planificateur)`, the figure in the danger color, bold for the missing-`WHERE` fact) and, when the session is in `Manual` mode, the sentence `La transaction manuelle est active : vous pourrez encore annuler avant de valider.`; the statement in a mono box with a red left border (several statements: the first five, then `+ N autres`); the typed field (placeholder = the expected word); the checkbox `Exécuter dans une transaction et ne pas valider automatiquement`; the confirm button labeled by kind and figure (`Supprimer 1 248 310 lignes`, `Modifier N lignes`, `Exécuter` when no figure or no verb fits) in the danger color; the hint `Entrée = Annuler`; `Annuler`. **The checkbox** is shown when the run can be put in a transaction (every statement transactional on this engine: not MySQL DDL), **checked by default**; in `Manual` mode it is checked and disabled (the statement runs in the transaction anyway); in `AutoCommit` mode, leaving it checked switches the session to `Manual` and runs the statements in the new transaction (the user then sees `Valider` / `Annuler`), unchecking it runs them auto-committed. Estimate: section 5.
13. **No new setting, no per-profile default mode, no `Staging` confirmation** in this phase (listed as follow-ups in the ADR).

## 4. Engine matrix

| | SQLite | PostgreSQL | MySQL 8.4 | SQL Server |
|---|---|---|---|---|
| begin / commit / rollback | `BEGIN` / `COMMIT` / `ROLLBACK` | `BEGIN` / `COMMIT` / `ROLLBACK` | `START TRANSACTION` / `COMMIT` / `ROLLBACK` | `BEGIN TRANSACTION` / `COMMIT TRANSACTION` / `ROLLBACK TRANSACTION` |
| savepoint | `SAVEPOINT n` / `ROLLBACK TO n` / `RELEASE n` | same | same | `SAVE TRANSACTION n` / `ROLLBACK TRANSACTION n`, no release |
| DDL transactional | yes | yes | **no, implicit commit** | yes |
| error inside a transaction | statement fails, transaction stays (some errors roll back: probe) | **transaction `Failed` (25P02 afterwards)** | statement fails, transaction stays; a deadlock rolls the whole transaction back (probe) | statement fails, transaction stays; `XACT_ABORT` or a severe error dooms it (`XACT_STATE() = -1`, probe) |
| not allowed inside a transaction | `VACUUM`, `ATTACH`, `DETACH` | `VACUUM`, `CREATE/DROP DATABASE`, `CREATE INDEX CONCURRENTLY`... | none (implicit commit instead) | `CREATE/ALTER/DROP DATABASE`, `BACKUP`, `RESTORE` |
| unrolled `ROLLBACK` | one level | one level | one level | **rolls back every nested level** (never use it for a savepoint scope) |
| probe | `sqlite3_get_autocommit` through the connection handle | `SELECT 1`: `25P02` = failed, else unknown | candidates in P15-06, else unknown | `SELECT @@TRANCOUNT, XACT_STATE()` |
| connection closed with an open transaction | rolled back | rolled back | rolled back | rolled back (the app also sends `ROLLBACK` first) |
| estimated rows of a `DELETE` / `UPDATE` | none (plan has no estimate) | child scan of `ModifyTable` | table access of the JSON plan | child of the `Delete` / `Update` operator |

## 5. Estimated impact (P15-11)

`ImpactEstimator` asks `ConnectionSession.ExplainAsync(..., PlanMode.Estimated, ct)` for a **single** `INSERT` / `UPDATE` / `DELETE` statement (`PlanEligibility.CanExplain`), under a hard cap of **3 seconds** (linked cancellation), never when the session transaction is `Failed`. The figure is the estimated rows of the **first descendant of the root that reports them**, never the root's own (zero on PostgreSQL). `INSERT ... VALUES` is not estimated (the row count is known: no figure). SQLite, an engine refusal, a timeout, parameters the engine cannot plan: **no figure, no error shown**, the dialog simply has no number and its button says `Exécuter`. A figure is always worded as an estimate (`environ`, `estimation du planificateur`). It is shown in the user's number format (`1 248 310` in French).

## 7. Risks (every card that touches one handles it explicitly)

1. **MySQL implicit commit** silently ends the user's transaction: `StatementTraits.ImplicitCommit` + the confirmation (decision 9); the designer and the grid commit never send `BEGIN` inside an open transaction (decision 8). MyISAM tables are not transactional: documented in the ADR, not detected.
2. **`SqlRunner.BeginAsync` inside a user transaction** (see section 1): every caller goes through the new scope of P15-09; a test per engine proves the user's transaction survives a grid commit and a designer apply.
3. **Shared connection**: `Valider` / `Annuler` / a run / a plan / a grid commit must not overlap. `ConnectionSession.BeginOperation()` is a counter (not a lock, no deadlock): the transaction buttons and `Run` are disabled while an operation of another kind is in progress. Two tabs running statements at once on one connection stays a known limit of the app.
4. **PostgreSQL failed state**: after one error every later statement fails with `25P02`; the app refuses upfront and offers `Annuler`; savepoint scopes recover it.
5. **SQL Server unnamed `ROLLBACK`** rolls back all nested levels: only used by `Annuler`, never inside a savepoint scope (the plan reader of P13-10 already uses `SAVE TRANSACTION`).
6. **Plan `Analyser` inside an open transaction**: PostgreSQL (warning `25001`, no rollback) and SQL Server (savepoint) are already safe; MySQL has no wrapper; P15-09 proves it per engine and refuses `Analyser` when the state is `Failed`.
7. **Impact estimate wrong or slow**: capped at 3 s, wording says estimate, per-engine rule proven in P15-11 on containers; a figure is never exact and never blocks the run.
8. **Connection lost mid-transaction** (SSH tunnel drop, server restart): the server has rolled back; `Valider` fails; the app shows the error and the probe failure and tells the user the session was lost; it does not try to reconnect (known limit, ADR).
9. **Long open transactions on production** hold locks and (PostgreSQL) block vacuum: the status bar shows the duration; no timeout in this phase.
10. **Shortcuts** `Ctrl+Alt+C` / `Ctrl+Alt+Z` are `AltGr+C` / `AltGr+Z` on many keyboard layouts and may type a character in the editor; every head card checks the binding against the editor and the existing bindings and **stops with a proposed fix** when it clashes (P13-14 precedent).
11. **Behavior change**: the grid commit and the designer apply now ask on Production; the card reports and the ADR say so.
12. **Head dialogs**: `Entrée` must not confirm (WinUI `ContentDialog.DefaultButton = Close`, Avalonia dialog with the cancel button as default); window closing with an async question needs a cancel-then-close-again pattern on both heads (nothing exists today).
