# P8-04 - Sql: reading generated keys after an INSERT

Status: todo
Depends on: P8-03

## Goal
After inserting a row whose key is generated by the database (identity, serial, AUTO_INCREMENT, rowid), obtain the key value so the grid row can show it and later be edited by key.

## Design decisions (final)
- Namespace `Squill.Sql.Editing`. `public sealed record InsertPlan(DmlStatement Insert, DmlStatement? KeyQuery)` and `public static InsertPlan DmlGenerator.PlanInsert(InsertRow edit, EditTarget target, DatabaseDialect dialect)` (a second method of the class of P8-03; `Generate` for an `InsertRow` keeps returning the plain insert).
- A key value is "generated" when its key column is `IsAutoIncrement` and is absent from `edit.Values`. When no key column is generated, `KeyQuery` is `null` and `Insert` is the plain insert. Only a **single** generated key column is supported; with two or more throw `NotSupportedException("composite generated keys are not supported")`.
- PostgreSql and Sqlite: ` RETURNING <quoted key column>` is appended to `Insert.Sql`, `KeyQuery` is null (the insert returns one row holding the key; the committer reads it). SqlServer: ` OUTPUT INSERTED.<quoted key column>` goes before `VALUES` (before `DEFAULT VALUES` for the no-value insert), `KeyQuery` is null. MySql: `Insert` unchanged and `KeyQuery = new DmlStatement("SELECT LAST_INSERT_ID()", [])`.
- `public static bool ReturnsKeyFromInsert(DatabaseDialect d)` tells the committer whether the key comes from the insert's own result (true for PostgreSql, Sqlite, SqlServer) or from `KeyQuery` (MySql).

## Out of scope
- Non-key generated columns (defaults, computed columns): not read back; the user re-runs the query to see them.
- Executing anything (P8-09).
