# P20-41 - Preview pane: `Appliquer` stores the text shown, line breaks as `\n`, and an untouched text changes nothing

Status: done
Depends on: P20-40, P20-33

## Goal
Bug found by the P20-40 drive (Done notes, step 7) on the WinUI AOT exe: select a cell, `Ctrl+A` then `Ctrl+V` of a 298,034-byte indented JSON (12,882 `\r\n`) into the preview pane, `Appliquer`, commit: the stored value is 285,152 bytes, every line break is a lone `\r` and no `\n` remains. A SQL client must store a predictable value from the pane. Decide what `Appliquer` stores, put the rule in Presentation with unit tests, keep both heads on it, and prove it on the AOT exe with a length and SHA-256 check as in P20-40.

Files today: `src/Squill.Presentation/Results/CellPreviewViewModel.cs` (`PrettyOptions`, `Refresh`, `OnTextChanged`, `Apply`, `Format`, `TryPretty`; reworked by P20-33, read it as P20-33 left it), `src/Squill.App.WinUI/Views/CellPreviewPanel.cs` and `src/Squill.App.Avalonia/Views/CellPreviewPanel.cs` (`_text`, its `TextChanged` handler, `Sync`), `tests/Squill.Presentation.Tests/Query/CellPreviewTests.cs`.

## Root cause (read in the code at `0cf55e5`)
1. **WinUI `TextBox` returns every line break as `\r`** (also the root cause item 4 of P20-40). The pane's `TextChanged` handler copies `_text.Text` into `CellPreviewViewModel.Text`, and `Apply` passes `Text` to `ResultEditorViewModel.TrySetCell` unchanged, so the cell gets `\r` line breaks. Nothing in Presentation looks at line breaks.
2. **The pane changes the value even when the user edits nothing** (same cause, not seen in a drive yet; confirm it in step 1 of the drive): `Refresh` shows `TryPretty(value)` for JSON; `Utf8JsonWriter` with `Indented = true` writes `JsonWriterOptions.NewLine`, which defaults to `Environment.NewLine` (`\r\n` on Windows). `Sync` writes that text into the WinUI box; the box then raises `TextChanged` (asynchronously, `_syncing` already `false`) with `\r` line breaks, so `Text != _original` and `IsDirty` becomes `true`: `Appliquer` is enabled without any edit, and `OnGridChanged` stops refreshing the pane (`if (!IsDirty) Refresh()`). A non-JSON value read with `\r\n` or `\n` has the same problem on WinUI.
3. **Re-indentation is display only**: `Apply` stores `Text`, it never calls `TryPretty`. The pane shows a JSON value indented (`Refresh`, and `Format` when the user asks), so an edited JSON is stored as indented by the pane plus the user's edit. In the P20-40 drive the pasted text replaced everything, so only the line breaks differed (285,152 = 298,034 - 12,882).
4. **Avalonia**: its `TextBox` keeps the text it is given (pasted `\r\n` stays `\r\n`), but `Enter` inserts `TextBox.NewLine` (`Environment.NewLine`, `\r\n` on Windows) while a value read from the database usually has `\n`, so an edited value can hold mixed line breaks. Same fix, no head change expected (check it with the characterization test below).

## Design decisions (final)
- **What `Appliquer` stores**: the text exactly as shown in the pane, with every `\r\n` and every lone `\r` replaced by `\n`; nothing else is changed (no re-indent, no minify, no trim; indentation, tabs, U+2028/U+2029/U+0085 and a final line break are kept). Why: the pane is a text editor, the user expects to get what they see; `\n` is the one line break every engine, JSON parser and both heads agree on, it removes the WinUI-only `\r` form and the Avalonia mixed form, and it gives the same stored value on both heads and on every OS. Rejected: storing the text as typed (gives lone `\r` on WinUI, a value no other tool reads as lines), keeping the original value's line-break style (the WinUI box has already lost it; guessing the style of a mixed or empty value is surprising), re-indenting or minifying at `Apply` (changes a value the user did not touch; minifying stays out of scope as in P20-31 ... P20-35). This differs on purpose from the in-place editor of P20-40, which stores the exact clipboard text: that editor never puts the value through a multi-line `TextBox`.
- **Untouched text changes nothing**: two texts that differ only by line-break form are the same draft. `IsDirty` compares the normalized forms, so selecting a cell, letting the WinUI box round-trip it, and leaving the pane never enables `Appliquer` and never writes; `Appliquer` is enabled only when the normalized text differs from the normalized value shown at `Refresh` (or after the last apply). A user who presses `Format` on a JSON whose indentation differs gets `IsDirty` true (that is an edit they asked for) and `Appliquer` stores the indented text with `\n`.
- **Shared rule** (Presentation, unit tested): `public static string NormalizeLineBreaks(string text)` on `CellPreviewViewModel` (next to `TryPretty`; not on `CellText`, whose summary says it is never used for the pane or commits). XML doc: `\r\n` and lone `\r` become `\n`; returns the same instance when the text has no `\r` (one `IndexOf('\r')`, then `string.Create` or a `StringBuilder` in one pass; no `Replace` chain that would turn `\r\n` into two breaks). `ArgumentNullException.ThrowIfNull(text)`.
- **`CellPreviewViewModel`** (apply these rules to the code as P20-33 left it, including its background validation):
  - `PrettyOptions` gets `NewLine = "\n"`, so `Refresh` and `Format` produce `\n` on every OS.
  - Keep `_original` normalized: set it from `NormalizeLineBreaks(value)` in `Refresh` and from the stored value in `Apply`.
  - `IsDirty = CanEdit && NormalizeLineBreaks(value) != _original` wherever `OnTextChanged` (or P20-33's split of it) sets it.
  - `Apply`: `var value = NormalizeLineBreaks(Text);` then `TrySetCell(_row, _column, value)`; on success `_original = value`, `IsDirty = false`. `Text` itself is not rewritten (the box keeps its caret and undo).
  - Validation keeps reading `Text` (JSON and `CellValueParser` treat `\r` like `\n` for every type the pane validates); `TrySetCell` validates the stored form again.
- **WinUI head** (`CellPreviewPanel.Sync`): write `m.Text` into `_text` only when `CellPreviewViewModel.NormalizeLineBreaks(_text.Text) != CellPreviewViewModel.NormalizeLineBreaks(m.Text)`. Why: otherwise every `ViewChanged` between the `Refresh` and the box's late `TextChanged` re-inserts the whole value (300 KB, caret back to the start), which also defeats P20-33's "fill the native box once". The `TextChanged` handler is unchanged. If P20-34 already added a paste handler with `SelectedText = text` to the pane, leave it: the normalization at `Apply` covers its `\r`.
- **Avalonia head**: no code change unless the characterization test shows otherwise; if it does, mirror the WinUI `Sync` comparison and say so in the Done notes.
- No new UI text, no new package, no `Application.Current.Resources` brush lookups (P20-02 guard).

## Out of scope
- The in-place editor (P20-40, exact value), the grid paste, export and copy (unchanged), minifying or re-indenting at `Apply`, a setting for the line-break style, keeping a `\r\n` style per value, the light theme look of the pane (P20-42), the long-paste popup and working strip (P20-34 / P20-35).
